3 Real-World Examples

1

Complex cross-system investigation

PES-1167

Issue: A Bloomberg curve file for 31 August was available, but the ingestion pipeline processed the wrong date. This caused the required curve data to be missing and downstream HSIEM index calculations to fail.

A Bloomberg ingestion failure required Sherlock to investigate across Airflow logs, S3, DataAPI configuration, manifests, SecAPI, Jira history, and source code. It connected the evidence into a complete failure chain:

Holiday calendar → wrong expected file → file skipped → missing SecAPI data → downstream index failure

Sherlock also identified that simply rerunning the job would reproduce the same failure because the underlying calendar logic had not changed. It recommended the correct configuration change and recovery sequence, which matched the eventual resolution.

2

Reusing a previously solved case

PES-1168 / PES-352

Issue: Citi uploaded a target portfolio successfully, but its client reported the request as failed because the API response contained additional fields that its Java parser did not recognize.

Sherlock found that the Citi portfolio issue in PES-1168 closely matched PES-352, where the same API/client behavior had already been investigated.

Rather than redoing the entire investigation, Sherlock reused the established resolution while verifying the important differences in the new case, including the stored portfolio, API response, schema, and current implementation.

It correctly concluded that no MerQube rollback was required and that Citi needed to update its parser to tolerate additional response fields. That is ultimately how the case was resolved.

3

Pinpointing the exact code change

PES-1197 / ENG-3205

Issue: Barclays needed the RADAR report filename to contain the next calendar day, but the existing {NEXT_REPORT_DATE} token represented the next index business day. Changing the existing token could therefore affect other reports that relied on its current behavior.

For a Barclays RADAR filename requirement, Sherlock determined that changing the existing {NEXT_REPORT_DATE} token would risk affecting other reports. Instead, it proposed introducing a new {NEXT_CALENDAR_DATE} token.

Sherlock identified the required changes across the report runtime, Admin validation, and BXIIRDS6 configuration, while explicitly identifying what should remain unchanged.

Most importantly, the engineering solution that followed implemented the same design Sherlock had proposed, with Sherlock documenting the solution before the corresponding human proposal and ENG ticket.

The Key Message

Sherlock is useful at very different levels of investigation.

For complex incidents, it can trace evidence across systems until it identifies the complete root-cause chain.

For recurring incidents, it can find and reuse institutional knowledge that would otherwise be buried in old Jira cases.

And when engineering work is required, it can move from diagnosis to a precise, scoped implementation recommendation, including what should change and, just as importantly, what should not.
