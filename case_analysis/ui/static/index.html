How the pieces connect.

One support case, start to finish: what triggers the work, what it reads, what it produces, and what feeds back into the next case. Dashed pills are not built yet.

  1. 01

    A case arrives

    Either an engineer starts one by hand, or the console notices a newly created support case and holds it briefly so the reporter can finish writing it up.

    Jira Checks every 60s Holds new case 5 min Manual launch Only cases created while running
  2. 02

    Check its own footing

    Before reasoning about anything it confirms it can actually reach the systems, and fast-forwards the repositories so conclusions are drawn against deployed code rather than a stale checkout.

    VPN AWS SSO ~/.merq_creds Repo fast-forward
  3. 03

    Recall what we already learned

    It looks for a playbook matching this failure class first. A hit brings the proven path and, just as important, the skip list of checks that wasted time last round.

    Playbook index Optimal path Skip list Vector recall by meaning
  4. 04

    Read the systems that hold the answer

    Only the sources the playbook points at, rather than everything at once. Whatever it could not reach is named in the report instead of quietly skipped.

    Airflow · Merq Airflow · Helix IndexAPI manifest SecAPI metrics DataAPI ingestion S3 listing Postgres GitHub code Read-only, SELECT only
  5. 05

    Explain it

    One support-first report: what happened, who is affected, the decision, what to do now, what not to do, plus a PE appendix with technical findings.

    Decision + certainty Do now / do not do Technical appendix Jira comment draft Proposes, never commits or posts
  6. 06

    Everything lands on disk

    Each run keeps its prompt, artifacts, logs, and report, so any conclusion can be audited later. Files are the record; search is built on top of them.

    Run folder per attempt Report + artifacts Full evidence trail One Postgres store Embeddings alongside cases
  7. 07

    Keep only the path that worked

    Once solved, it retraces its own investigation and keeps the steps that changed the conclusion, plus the dead ends worth skipping. That becomes the playbook the next case starts from.

    Distill optimal path Write playbook Record skip list

    Feeds back into step 03 — this is what makes later cases shorter and cheaper.

  8. 08

    When the case closes

    On closure it writes the retrospective: the timeline, what actually fixed the problem, and what would have caught it earlier.

    Retrospective on close Jira status
  9. 09

    When the same thing keeps happening

    Once a failure class shows up in three or more cases, it drafts a support-facing runbook so the issue stops arriving as a fresh investigation at all.

    Runbook draft at 3+ cases Publishing needs a human Guided fix for easy repeats
